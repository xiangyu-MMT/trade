### 业务分析

- 用户的成交额要求只改变市场成交额口径和显示方式，不推定其撤销个股候选或涨跌家数的原ST排除要求。完整市场统计仍由程序计算，AI只接收汇总和范围内候选。

## 3. REQ-001 逐条分析（需求修订 R11）

### 3.1 业务范围与使用流程

使用流程为：**配置候选与交易知识 → 手动触发或运行时每小时刷新 → 获取全市场与候选数据 → 程序计算 → Codex 对照归档推导 → 查看 HTML 结果 → 系统拟计划、翔宇确认或自行记录计划 → 翔宇交易并回填 → 复盘并确认知识修订。**

多机自动同步、手机专用界面、付费行情采购、自动挑选未配置的交易品种、预测模型训练、全历史策略回测和全量研报库均未被提出为本期交付；如需要，另行确认范围。

| 全市场与行业盘面 | 涨跌家数、涨跌停、成交额前 10、量能与资金方向 | 符合过滤范围的汇总或底层数据，涨跌停及封板状态，行业涨跌幅和资金指标 | 免费覆盖的首要风险；资金、封板率需固定定义与来源 |
| 融资与 ETF 份额 | 判断资金及结构变化 | 报告日期、余额/份额、增减与公布时间 | 按真实发布频率使用；ETF 份额不以成交量或成交额替代 |
| 跨市场 | 解释外部环境与模式 | 美元、10 年美债、黄金、石油、10 年 TIPS 的指定序列 | 部分免费源是日频；“中证金融”“微盘股”及具体宏观代理仍需核对 |
| 逻辑证据 | 解释高股息、行业周期、主线、流动性等逻辑是否有依据 | 已归档定义、用户资料及可获取的分红/行业/公开信息等证据 | 行情上涨本身不足以证明逻辑成立；证据不够时明确保留判断 |
| 用户交易资料 | 计划检查与复盘 | 确认计划、用户填写的执行信息和复盘说明 | 输入来源已明确为用户回填；字段在后续任务卡中具体化 |

数据处理顺序为：**优先免费正式接口 → 其他真实免费来源补充 → 记录尝试与残余缺口 → 影响到的判断降级或等待。** 补充来源时要保留单位、币种、源日期、发布时间与口径，不能静默拼接不同定义的数值。供应商称“资金流入”的指标也需要注明其算法口径。

全市场观察是数据成本与覆盖的主要约束。iFinD 免费接口是候选来源，其免费 EDB 缺口表明不能假设单一免费接口覆盖全部宏观需求；API/MCP 是接入方式，不改变底层账号授权和数据内容。具体提供方按后续接入结果决定。

### 3.5 程序与 Codex 的职责

| 程序负责的确定部分 | Codex 负责的理解部分 | 由翔宇确认的内容 |
|---|---|---|
| 数据归一、日期和单位检查、过滤、排序、指标计算、明确规则检查、计划记录与图表呈现 | 对照归档解释逻辑、趋势与模式；呈现支持与反对证据；拟定计划和复盘建议 | 新增/修订逻辑技术模式、计划草稿和实际交易决定 |

初始逻辑档案以翔宇已确认熟悉的五类为起点：红利高股息、行业周期反转、主线趋势、宽基流动性与估值修复、大跌后超跌博弈反弹。初始模式保留科技吸血单边、增量普涨、缩量阴跌、高切低、防御、进攻、超跌反弹等描述；这些名称还需要结合证据形成可引用定义，归纳草稿经翔宇确认后使用。超跌反弹可以同时作为交易出发点和市场状态，不能在归档时强行只留一个层面。

归档须能区分草稿与已确认内容，并让一次分析引用当时使用的版本。后续知识修订不改变旧报告、旧计划当时的依据。程序计算结果可以复算；Codex 的原始输出与所用输入应可追溯，不承诺多次生成措辞完全相同。

明确的模式条件可由程序检查，尚不能量化的部分由 Codex 解释。模式可以存在不同侧面，例如量能变化与进攻/防御描述；A1 建议保留多种证据与冲突，不为了输出单一标签强行消除分歧（D2 已确认，见第 7 节）。未提供统计依据时，呈现“符合哪些条件”与“哪些条件不支持”，不输出编造的胜率数值。

新规则先归档为待确认内容，翔宇确认后供后续分析使用。系统的任务是应用和协助完善交易体系，不能因一次结果好坏就自动改写已确认规则。

### 3.6 计划、执行与复盘

计划包括已确认的字段：**标的；逻辑/技术/模式依据；买入条件；退出条件；仓位与风险限制；有效期。** 计划由系统先拟，翔宇确认，也可由翔宇直接记录。

A1 建议计划保留草稿、已确认、执行记录、复盘之间的关系。小时刷新可提示原依据变化和计划偏差，并提出修订草稿；已确认计划的原内容保留，避免后续行情刷新覆盖事前判断。修改或结束计划由翔宇决定，具体操作流程在任务卡与设计阶段细化。

板块/指数方向与实际交易品种应明确关联。若未指定要买卖的 ETF 或个股，先形成方向级观察计划，并注明执行标的待补充，不由系统擅自挑选一个同名基金（D1 已确认，见第 7 节）。仓位或风险限制缺少个人规则时保留为待补充，不用无依据的数值填满表单。

执行信息由翔宇回填。系统可以据已填写内容对比计划，不能声称已看到未接入的券商成交，也无法阻止翔宇在交易软件中进行计划外买卖。“无计划不交易”在辅助系统内体现为关联计划、标记计划外记录和执行偏差；执行纪律仍由翔宇落实。

复盘应区分当时逻辑/模式判断、计划规则、实际执行和结果，允许证据不足或原因未明；一次盈利不等于规则正确，一次亏损也不能直接归因为未按计划执行。复盘形成的知识修订经翔宇确认后归档。

### 3.7 触发、时间与异常边界（A1 建议）

| 情况 | 建议的业务表现 |
|---|---|
| 手动按钮、运行时每 1 小时到期 | 触发一轮取数、计算、Codex 推导和页面更新；展示当前进度 |
| 一轮未完成又收到触发 | 避免并行覆盖同一轮资料或重复生成计划；是否合并排队由技术设计确定 |
| 盘中运行 | 行业排名使用当日累计成交额；未完成日线和周线标明是形成中数据 |
| 盘前、周末、休市 | 使用最近可用交易日的数据并明确日期；不把上一交易日成交额显示成今日成交额 |
| 退出系统、电脑休眠或断网 | 运行期间的定时能力随服务可用性变化；恢复后显示中断情况，再获取最新数据，避免补跑大量旧轮次 |
| 部分数据缺失 | 尝试其他真实免费源；仍缺失则标出受影响字段与结论，不把不完整全市场统计当成完整统计 |
| Codex 未登录、额度或调用失败 | 保留已获取数据、程序结果和历史报告；当轮 AI 解读明确失败，不将旧解读标为新结果 |
| 配置对象无法识别 | 显示具体无效项；不默认为其他证券。有效项能否继续按影响明确显示 |
| 计划已确认后再次刷新 | 原计划保持可追溯，新的判断产生提示或修订草稿 |

这些是需求层的异常表现建议，尚未设计正式测试用例。具体超时、重试、缓存和调度算法由 Codex 在技术设计中决定。

### 3.8 展示与非功能要求

首页建议只保留四类内容：市场判断与时点、少量候选及主要理由、计划提醒、关键图表。完整候选、指标、支持/反对证据、归档与数据缺口按需展开。具体首屏数量和图表选择在任务卡与设计中明确，不把历史答疑中的示意数字当成已签要求。

页面应显示数据截至时间和分析生成时间，支持查看历史轮次和计划关联。缺数据或结论不充分时，允许清楚显示“等待”“证据不足”，不会为了填充首屏而制造推荐。

按钮触发、定时调用数据源和 Codex 需要本地运行能力；导出的自包含 HTML 可以离线阅读某轮结果，交互运行界面需要运行服务支持。这是交付形态判断，具体技术栈留待设计。

其他边界：

- Mac 与 Windows PC 均为目标环境；当前 Mac CLI 可用不代表 Windows 或所有行情客户端已验证。优先评估跨平台 API 路径，客户端/DLL 依赖单独核实。
- 若使用 Node，按工作区约束仅用 22.x。实际安装方式、浏览器兼容和 Windows 最低版本在设计时声明。
- 归档、计划和记录需要持久保存。跨设备运行与自动同步是不同能力，首期本地保存并提供可迁移文件；D3 已确认首期不自动多机同步，见第 7 节。
- 行情保持免费优先约束，源缺口尽力补齐后标注；AI 使用已有 Codex 会员，实际额度和登录按运行设备核实。
- 凭据不进入 HTML 或 Git；程序不接收下单权限。实验室网络、设备和其他项目不属于本项目实现范围。
- 尚无运行时长或性能实测，本分析不承诺生成报告的固定秒数。应能显示进度、失败原因及最近成功轮次。
