## 目标与边界

建立本地版本化档案与明确确认，给报告/计划保留稳定引用。

| 任务卡验收标准 | 方案响应 |
|---|---|
| AC01、AC02、AC03 | SQLite 通用版本对象保存逻辑/技术/模式，种类可交叉引用，草稿与确认分离；种子条目只录已确认原话。 |
| AC04、AC06 | 对象 ID + revision 为引用；修订追加新行；读取最新已确认版时不被更新草稿覆盖。 |
| AC05 | 输入、引用及版本冲突返回明确错误；迁移导入校验后在事务中合并，不覆盖冲突历史。 |

本方案沿用已签 T1 的要做/不做范围与 A1 的 D1–D3 决定：人工指定实际品种、依据不足保留观察/等待、本地文件可迁移；没有自动交易、付费行情或多机云同步。

## 方案与选择依据

| 关键选择 | 理由及处理 |
|---|---|
| SQLite + JSON 载荷 | 标准库可用，事务支持确认和记录一致性；数据存 .local/trade.sqlite3。比散落并发文件更适合本地多请求，首期无云端服务。 |
| 追加修订，确认特定版本 | 确认记录含 actor、时间和 revision；已确认载荷不可原地改写；新修订初始为 draft。 |
| 通用对象与运行记录分表 | objects 存 object_id/kind/revision/status/payload/created_at/confirmed_at/confirmed_by；runs 存取数/事实/AI轮次；执行和复盘用独立对象关联原计划版本。 |

实现文件：src/trade_assistant/store.py；src/trade_assistant/knowledge.py；src/trade_assistant/defaults/knowledge.json

## 接口、数据与错误约定

1. Store 每次操作独立连接，启用外键、busy_timeout 和事务。ID 采用 UUID；JSON 写入仅接受有限数值；数据库版本通过 PRAGMA user_version 管理。

2. Knowledge.create / revise / confirm / list / get_versions 接收明确对象和 expected_revision；冲突返回 conflict，缺对象 not_found，无效结构 validation_error。

3. 已确认知识读取按对象分别取最大已确认 revision；新 draft 不替换正在使用的旧 confirmed。报告中保存 id@revision 及输入副本。

4. 迁移格式 archive_version=1，包含配置、对象版本、运行和关联记录；不含账号密钥或 Codex 登录信息。相同键内容冲突则整次拒绝，完全一致可幂等合并。配置文件可独立迁移。

5. 初始化只注入用户原话对应的五类逻辑、已确认的技术要求和模式描述，注明来源；额外阈值或 AI 归纳条目保持 draft。

跨任务共用约定：不可变 run_id 与 object_id@revision；所有源时间与生成时间分开；知识/计划确认由明确用户动作完成；数据缺口可追溯。后续若协议实质变化，在受影响方案和实现记录中说明，不无声更换。
