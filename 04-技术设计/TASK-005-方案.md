## 目标与边界

形成可确认、可追溯的计划与人工记录，将复盘建议送回待确认知识档案。

| 任务卡验收标准 | 方案响应 |
|---|---|
| AC01、AC02 | 计划作为版本对象，系统草稿/用户手工录入共用字段与确认流程；引用原分析和知识版本。 |
| AC03、AC05、AC06 | D1/D2 约束执行标的与缺项；旧计划保留；复盘结果形成 draft 知识，不自动确认。 |
| AC04、AC07 | 人工执行记录关联明确 plan_id@revision；无计划或无证据明确标识，存储/模型失败不丢原文。 |

本方案沿用已签 T1 的要做/不做范围与 A1 的 D1–D3 决定：人工指定实际品种、依据不足保留观察/等待、本地文件可迁移；没有自动交易、付费行情或多机云同步。

## 方案与选择依据

| 关键选择 | 理由及处理 |
|---|---|
| 观察计划与具体品种计划分开 | 未映射实际 ETF/个股时只生成 observation；用户指定可交易品种后才形成具体计划草稿，系统仍不执行买卖。 |
| 确认特定版本，修订生成新草稿 | 同 Store 对象机制；小时刷新只能提示依据变化，不改原确认内容。 |
| 回填是用户提供的事实 | 字段含发生时间、动作、实际品种、数量/金额/价格（可缺）、说明和计划引用；缺失不推断为发生或未发生。 |
| 复盘使用原计划+真实回填+当时事实 | 分别讨论判断、计划、执行、结果；原因未明可保留；知识改进建议需用户动作纳入草稿并再确认。 |

实现文件：src/trade_assistant/plans.py；src/trade_assistant/schemas/{plan,review}.json；src/trade_assistant/prompts/{plan,review}.txt

## 接口、数据与错误约定

1. PlanPayload：asset_id、execution_asset_id（可空）、plan_type、basis（logic/technical/mode）、entry、exit、position_risk、validity、missing、run_id、knowledge_refs。系统生成后先 draft；必要字段缺少时保留待补充。

2. create_manual 和 draft_from_run 均在服务端验证候选/执行映射。confirm 指定 revision 和用户动作；观察计划可确认观察内容但不会显示成具体可执行品种计划。

3. ExecutionPayload 保存原始备注、时间、方向、数值及 plan_ref。未关联计划标为计划外；关联未知/不一致版本返回明确错误。执行回填本身不确认计划。

4. 偏差检查基于已有字段：计划外、早于确认、品种不一致、有效期/条件或记录缺失等只在依据够时判断；无法解析的自然语言条件显示需要人工复核。

5. Review 调用同一 CodexBridge，输出事实对照、可证实偏差、无法判断项及知识建议。新知识写入 draft，保留 review_ref；对旧对象修订必须引用其 ID 和原版本。

跨任务共用约定：不可变 run_id 与 object_id@revision；所有源时间与生成时间分开；知识/计划确认由明确用户动作完成；数据缺口可追溯。后续若协议实质变化，在受影响方案和实现记录中说明，不无声更换。

## 风险与处理

- 没有券商通道，系统无法感知用户未回填的交易，也不阻止外部操作。
- 默认不编造价格、仓位和止损数值；用户可在草稿中补充自己的规则，确认动作与项目签字分离。
